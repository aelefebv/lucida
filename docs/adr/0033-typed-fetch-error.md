# Typed `FetchError` + injectable `RetryPolicy` at the fetch boundary

Status: Accepted.

## Context

The CPU cache once decided whether to retry a failed fetch by matching the error message
against `"404"` and `"malformed"`. Any new permanent failure that matched neither, such as a
missing wire-format registration, was wasted on a retry. The source that raises the error
knows what kind it is. The consumer's catch block does not.

## Decision

`ContentSource` rejects with a `FetchError` whose `kind` comes from a small closed set:
`permanent`, `transient`, `pending` (generated bytes not ready yet), or `abort`. A standard
`AbortError` counts as `abort`. The cache
dispatches on the kind through an injected `RetryPolicy`. Chunks use `OnceTransientRetry`, and
the proxy path uses `NeverRetry`. A plain `Error` still works: `classifyFetchError` falls back
to the old substring rule and logs `cache.untyped_fetch_error`, so untyped throws surface
instead of hiding.

## Rejected alternatives

- Keep string matching and widen the substrings. Every new permanent error needs a matching
  edit on both ends, and the match had already drifted.
- A flat error-code enum with no `kind`. Each consumer would keep its own mapping from codes to
  the few outcomes the cache acts on (retry, fail, clean up silently).
- One error class per kind. The `kind` field gives the same exhaustiveness without three
  `instanceof` chains. A kind that later needs its own fields, such as a server-suggested retry
  delay, can become a subclass without touching the others.
