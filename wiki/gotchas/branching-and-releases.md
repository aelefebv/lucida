# Branching and Releases

How code lands in lucida and how releases happen, in one place. The shape is **trunk-based** with `release-please` automating semver bumps from Conventional Commits. Image tags (not git branches) model "what's deployed where."

## The shape

`main` is the only long-lived branch and is **always release-ready**. Feature work happens on short-lived branches that PR into `main`. After merge, the branch is auto-deleted. Subsequent slices branch off the freshly-updated `main` — no rebasing dance for serial work.

Per-slice PR cadence: open one PR per slice. Don't batch multiple unrelated slices into one PR — small PRs review faster and bisect cleanly when something breaks.

## How releases happen

`release-please` watches Conventional Commits on `main` and decides version bumps:

- `feat:` → minor bump (e.g. `v0.2.0` → `v0.3.0`)
- `fix:` or `perf:` → patch bump
- `BREAKING CHANGE:` footer → major bump
- `docs:`, `chore:`, `style:`, `test:`, `ci:`, `refactor:` → no release; included in the next release's changelog when one happens

Whenever a bumping commit lands on `main`, release-please opens or updates a release PR (titled `chore(release): ${version}`, per the `pull-request-title-pattern` in `release-please-config.json`) with the autogenerated `CHANGELOG.md` entry. **The maintainer manually merges that PR when a release is desired** (auto-merge is OFF per [[decisions/0022-manual-merge-release-please-on-main]]) — this lets you batch related changes into one release. Merging the release PR pushes a tag, which triggers the image-publishing workflow.

Why manual-merge: a solo or small-team project frequently merges a `fix:` immediately followed by a related `feat:`. Releasing each separately is noise; the manual gate is one click and gives you the batching for free.

## Environment promotion uses image tags, not branches

A common anti-pattern is `dev`/`staging`/`prod` git branches. Lucida explicitly does not do this. Instead:

- The dev cluster pulls the latest tag (e.g. `:latest` or `:main`)
- The prod cluster pins a specific release (e.g. `:v0.5.3`)
- Promoting a release to prod is a manifest edit (`kubectl set image`), not a `git merge`

This matches how the deployment artifacts in `extras/deploy/` are designed (per [[decisions/0021-deployment-artifacts-as-reference-templates]]) and avoids the well-known drift problem where environment branches accumulate merge conflicts and "what's deployed where" diverges from "what's in the branch."

## Why branch protection on `main` is load-bearing

Without branch protection, a typo committed straight to `main` could trigger an unintended release once the auto-release pipeline is wired up. With it, every change goes through a PR + green CI before it can become an image. **This is a setup prerequisite** documented in `extras/deploy/RUNBOOK.md`.

The settings that matter:
- Require a PR before merging
- Require all CI status checks to pass before merging
- Disallow direct pushes to `main`
- Enable "automatically delete head branches" on merge

These are configured in repo Settings → Branches → Add rule for `main`, or via `gh api`.

## Conventional Commit discipline

The conventional-commit type drives version-bump decisions, so a `feat:` mislabeled as `chore:` silently blocks a release that should have happened, and a `chore:` mislabeled as `feat:` produces a noise release. Discipline is human; the cost of getting it wrong is bounded:

- Squash-merge PR titles can be edited at merge time — re-read the title before clicking the button
- Version bumps can be corrected post-merge by amending the open release PR before merging it

The benefit is that release notes stay accurate without anyone hand-writing them, and adopters can read `CHANGELOG.md` to decide whether to upgrade.

## Why not GitFlow

GitFlow (long-lived `develop` + release branches + hotfix branches) is designed for slow-cadence software with multiple supported in-flight versions. A solo / small-team OSS project with a single deployable image drowns in its ceremony. Skip it.
