# WASM Rebuild After Rust Changes

## The footgun

Touching [lucida-core](../systems/crates/lucida-core.md) Rust source doesn't automatically reflect in the running web client. The WASM bundle is generated into `lucida-core/pkg/` (which is gitignored — see below — not committed) and only regenerated by `pnpm run build:wasm`. The web app imports it through the live `"lucida-core": "link:../lucida-core/pkg"` package alias in `lucida-web/package.json`; Vite excludes that package from dependency optimization so it does not retain a second generated copy.

Symptoms:

- Compiles cleanly: `cargo test -p lucida-core` passes.
- Browser shows old behavior. New tests pass; the visible app doesn't reflect the change.
- Worse: the JS-side TypeScript types in `lucida-core/pkg/lucida_core.d.ts` are stale, so a new method you added in Rust **isn't visible to TS** until you rebuild.

## The dev loop

The canonical loop is `./scripts/dev.sh`. It brings everything up to date in
one command and **auto-rebuilds the WASM pkg when either its build inputs or its
generated artifacts changed**. `scripts/wasm-dev-fingerprint.sh` hashes every
workspace Rust source and crate manifest plus the root manifest/lockfile,
toolchain pin, and build recipe. A second fingerprint covers the complete
wasm-pack output (WASM, JavaScript, declarations, and package manifest). The
script skips only when both match the atomically written
`lucida-core/pkg/.dev-build-state`; a missing/unreadable input or partial pkg
fails closed into a rebuild. Hashing bytes rather than mtimes means a checkout
does not trigger needless work. Pass `--wasm` to force a rebuild.

Port ownership is checked early for a useful warning but enforced only after
WASM, web dependencies, and the server binary are fresh. That ordering prevents
a stale orphan on `:9876` from blocking the rebuild itself. Stop the reported
listener, or explicitly pass `--replace` to send it `TERM` after the builds.

The manual fallback, for an ad-hoc rebuild without the full loop:

```
cargo test -p lucida-core
cd lucida-web && pnpm run build:wasm
```

`build:wasm` runs `wasm-pack build --target web --out-dir pkg -- --locked`. After it, refresh the browser; Vite reads the new `lucida-core/pkg/` files through the live link.

For pure-TS changes in [lucida-web](../systems/crates/lucida-web.md), no rebuild is needed — Vite hot-reloads.

## pkg/ is generated, not committed

`lucida-core/pkg/` is gitignored at three levels (root `.gitignore`, `lucida-core/.gitignore`, and `lucida-core/pkg/.gitignore` = `*`), so `git ls-files lucida-core/pkg/` is empty. A fresh clone therefore **cannot** run the web app without the Rust/wasm toolchain — `README.md` lists `wasm-pack` as a prerequisite and the pkg must be built on first run (`./scripts/dev.sh` does this for you).

The build recipe and pinned toolchain are fingerprinted too, so changing the
wasm-pack invocation or compiler pin invalidates the state automatically. The
`--wasm` escape hatch remains useful when investigating an external toolchain
problem, but it is no longer required to repair an untrusted hash verdict.

## What to do

- **Prefer `./scripts/dev.sh`** — it folds the WASM rebuild into the normal loop, so it's no longer a step you can forget.
- **If TypeScript reports an unknown WASM method**, your `lucida-core/pkg/lucida_core.d.ts` is stale — rebuild (`pnpm run build:wasm` or `./scripts/dev.sh --wasm`).
- **For Python (`lucida-py`)**: the equivalent is `cd lucida-py && maturin develop` after Rust changes. README documents this.
