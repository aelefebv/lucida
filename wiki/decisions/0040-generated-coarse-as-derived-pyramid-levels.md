# Generated coarse as derived pyramid levels

Status: Accepted

## Decision

Coarse residency is represented as an explicit level pointer in image metadata.
If an existing source pyramid level fits the configured coarse bounds, the
coarse pointer references that source level. If no source level fits, the server
creates a generated derived level in a server-managed cache associated with the
Lucida store.

Generated coarse levels are append-only metadata additions. They do not reorder,
replace, or mutate source levels, and a level index must not be reused for a
different generation config. If the generation config changes, the server
publishes a new derived-level identity or metadata snapshot.

Generated coarse never mutates the user's/source Zarr, including server-local
file path datasets. Generated bytes live in the derived cache and are keyed by
source content identity, generation config, image identity, derived level
identity, and chunk key.

The chunk resolver becomes source-aware: source levels resolve against source
storage, while generated levels resolve against the derived cache. Once a
generated chunk is materialized, it is served through the normal chunk path.

Initial dataset-open state includes source levels plus already-cached generated
levels. New generated levels and per-chunk readiness arrive later as
server-authored metadata/readiness deltas, not document commands and not proxy
catalog deltas. Generated availability bumps an asset/availability epoch, not a
user document-content epoch.

PRD: #672.

## Why

The viewer needs coarse fallback for every image/field, but datasets do not
always contain a source pyramid level that is small enough to be safe as a
whole-dataset context representation. Generating a bounded coarse level gives
Lucida a predictable fallback while preserving the user's source data.

Representing generated coarse as a derived pyramid level keeps the rest of the
pipeline simple. Planning still emits normal `level/t/c/z/y/x` chunk keys,
server chunk serving still returns chunk bytes, CPU cache still decodes chunks,
and the renderer still samples chunk atlases. The only new responsibility is
that metadata says which level is coarse and the resolver knows which backing
store owns that level.

Keeping generated coarse in a store-owned derived cache preserves the audience
split from [Three-Output Import Model](0005-three-output-import-model.md). Clients see image
metadata and fetch routes; the server keeps private source handles, cache
identity, and resolver bindings. It also keeps local-file saved-view behavior
compatible with [Local-File Datasets Are Personal-Only in Saved Views](0014-local-file-datasets-personal-only-in-saved-views.md):
Lucida can use server-local files without writing derived bytes into the user's
source path.

Explicit pending/readiness state prevents generated chunks from looking like
transient fetch failures. A chunk request still means "send bytes if
materialized now"; generation progress is communicated separately.

## Consequences

- `MultiscaleInfo` or equivalent image metadata owns the coarse level pointer
  plus generated-level provenance/config.
- `LevelGeometry` remains geometry-only.
- Source pyramid levels remain the normal detail choices; generated coarse is
  tier metadata by default.
- Server binding state needs a derived-level registry and a resolver that can
  dispatch source levels to source storage and generated levels to the derived
  cache.
- Dataset-open state must merge source metadata with already-cached generated
  metadata.
- Metadata/readiness deltas update client scene state, bump planning or
  availability epochs, and cause normal chunk re-requests after readiness.
- Chunk requests for not-yet-materialized generated chunks return explicit
  non-error pending status. Real misses return unavailable/error status.
- Cache writes must be atomic from the client's point of view: write temp data,
  close/fsync where practical, rename into place, update resolver-visible state,
  then publish readiness.
- A server-wide coarse generation service owns global concurrency, priority
  queues, cancellation tokens, viewer-interest hints, dedupe, readiness state,
  and cache identity.
- Generation is lazy and backgrounded. Dataset open/import does not block on
  generated coarse.
- Generation is demand-driven and proactive: current visible work first,
  predicted T/Z/channel work next, and background fill last.
- Stale generation can be preempted or canceled when viewport interest changes,
  especially during T/Z scrubbing.
- The first implementation targets server-mediated datasets, including
  server-local file paths. Browser-side direct fetch and protocol-local fetch are
  future work.

## How this decision should show up in code

- `lucida-store` import/binding metadata can represent source levels plus
  generated derived levels without mutating the source manifest in place.
- `lucida-server` maintains generated-level cache identity, atomic publish, and
  source-aware chunk resolution.
- `lucida-protocol` carries generated-level metadata/readiness deltas and
  explicit pending/unavailable chunk statuses.
- `lucida-core` / scene metadata can apply generated-level deltas and expose the
  coarse pointer to planning.
- `lucida-web` treats generated chunks as normal chunks after readiness and does
  not rely on proxy catalogs for fallback availability.
