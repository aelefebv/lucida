## What to build

Implement the first generated-coarse materialization path. When no source pyramid level satisfies the coarse bounds, the server should create bounded per-image/per-field coarse chunks in the derived cache, publish them atomically, and reuse them across reopen when the source identity and generation config match.

This slice is about correct generation, cache identity, atomic publish, and reuse. Advanced viewer-interest scheduling, cancellation, and fairness can stay simple until the follow-up scheduling slice.

## Acceptance criteria

- [ ] Coarse selection uses an existing source level only if it fits configured `coarseMaxLongAxis` and `coarseMaxBytesPerImageChannel` style bounds.
- [ ] If no source level fits, the server appends a generated derived level after source levels without mutating source data.
- [ ] Generated coarse is per image/field and per channel, not per well.
- [ ] Generated chunks favor one chunk per image/channel when within bounds, otherwise a small bounded grid.
- [ ] Generated bytes are written to the derived cache with identity keyed by source content identity, generation config, image identity, derived level identity, and chunk key.
- [ ] Writes are atomic from the client perspective: partial writes are not published and completed chunks become ready only after resolver-visible commit.
- [ ] Reopening the same unchanged dataset/config reuses already-generated coarse metadata and chunks.
- [ ] Dataset open/import does not block on generation.
- [ ] Tests cover source-level fit selection, generated-level append behavior, no source mutation for local/server-mediated paths, atomic publish, and reopen reuse.
