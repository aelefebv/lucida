# CPU Cache

`lucida-web/src/pipeline/fetch/` — host-side cache between the network and the GPU. `cpuCache.ts` (~1230 lines) is the entry point: it owns inline implementations of submit/schedule/deliver/eviction plumbing while delegating distinct concerns to a handful of collaborators. It is not a thin few-line fan-out. See [`cpuCache.ts` split into `pipeline/fetch/` modules](../../decisions/0032-cpucache-split-into-pipeline-fetch.md) for the directory-layout philosophy.

This is the **sole** chunk fetch path.

## Key collaborators

`cpuCache.ts` wires roughly five durable collaborators (the rest of the directory is types/telemetry/wire helpers):

- **stores** — `ChunkStore` (`chunkStore.ts`) backs the detail/main store and the coarse/minimap overview store. They have separate budgets/LRU behavior rather than one combined ordering.
- **scheduler** — `Scheduler<Req>` (`scheduler.ts`) over `FairPriorityQueue` (`fairPriorityQueue.ts`): persistent per-dataset pending ownership, round-robin workspace fairness, local priority heaps, and in-flight concurrency/byte caps. Detail/coarse buckets both make progress without one dataset replacing another's queue.
- **eviction policies** — `eviction.ts`: overview LRU plus the detail store's `TieredPolicy`. Tier order comes from `InteractionModeDetector`.
- **content source** — the chunk-only `ContentSource` over the WebSocket bridge.
- **decode pool** — `decodePool.ts` + `decode.worker.ts` (Raw / LZ4 / Zstd + uint8/bool/uint16/float32 normalization to GPU-ready u16).

Supporting modules include typed retry errors (`pending` means generated bytes are not ready), telemetry, rejection tracking, delivery state, and the binary wire codec. Missing chunks re-enter through `markChunkMissing`.

## Why a CPU cache between network and GPU

Three problems all want to be solved in one place:

1. **Decoding is parallel** but bounded by the decode worker pool size, which is **hardware-derived, not a fixed constant** — `defaultPoolSize()` is `Math.max(2, Math.floor(cores/2) - 1)` over `navigator.hardwareConcurrency` (`decodePool.ts`), so it varies per machine (≈3 on an 8-core box). If the network out-paces decode, requests pile up; if decode out-paces upload, decoded bytes sit waiting. A central cache lets fetch and decode and upload each go at their own rate without coupling.
2. **Re-fetch on GPU eviction is wasteful** if the bytes are still in CPU memory. The worker can evict an atlas slot under memory pressure; the CPU cache holds the decoded bytes long enough to re-upload without going back to the network.
3. **Tier-aware eviction lets the cheap stuff (prefetch, demoted) go first.** Without tiers, LRU evicts whatever's oldest, which often happens to be the most expensive thing to re-fetch (overview/minimap data covers the whole dataset).

## Submit → schedule → decode → deliver

Each tick:

1. **Stage** — TickCoordinator plans every visible dataset and finishes roster/label work before publishing. A later-dataset exception leaves the prior planning generation, worker cold state, and fetch state intact.
2. **Publish** — TickCoordinator calls `cpuCache.publishPlanningCycle(publications)` once for the workspace. Validation finishes before mutation; each dataset owns its persistent wanted map, omitted owners alone are cancelled, sent/rejection state resets once, and the scheduler drains once. `submit(plan)` remains an owner-scoped compatibility surface; `publishPlanDeltas` applies request upserts/removals without revisiting stable wanted work.
3. **Schedule** — schedulers launch up to `maxConcurrentFetches` (= decode pool size × `FETCH_CONCURRENCY_MULTIPLIER`, the multiplier being 3; so it tracks the hardware-derived pool size — ≈9 on an 8-core box, not a fixed value), bounded by `maxBytesInFlight` (32 MB). Detail and coarse chunk requests are interleaved when both lanes have work. If only one lane has demand, its cache bucket can borrow unused budget from the other lane; if both lanes have demand, each keeps its standard allocation.
4. **Fetch** — `contentSource.fetch(req)` returns bytes via the WebSocket bridge.
5. **Decode / insert** — decoded chunks land in the detail or coarse cache bucket with priority, residency tier, and wanted generation stamped from the latest submit that still wanted the in-flight request.
6. **Deliver** — decoded wanted entries enter an incremental fair ready heap. The uploader asks constant-time tier-demand counters, then pulls only what its frame budget can consume from `getDeliverable()`; there is no per-frame cache scan, global sort, or `Array.from` copy. After dispatch, it calls `cpuCache.markSent(delivery)`.

## Eviction tiers

Eviction is not one global ordering. The overview store is isolated from the detail store. Within detail, `EvictionTier` has `prefetch`, `demoted-detail`, and `active-detail`; `TieredPolicy` evicts cheapest-tier-first.

**The detail store's tier order is interaction-mode-dependent.** `getTierOrder(mode)` rotates it: panning and idle evict `prefetch → demoted-detail → active-detail` (cheapest losses first), but **scrubbing protects the prefetch tier** (next-time-step chunks the user is skimming) by demoting it last: `demoted-detail → active-detail → prefetch`.

`lane: "minimap"` chunks land in the `overviewStore` (coarse) so the minimap is isolated from detail churn. Combined with the planner emitting minimap at priority 0, the effect is "fetched first, evicted outside the detail budget." See [Minimap Lane with Highest Priority](../../decisions/0023-minimap-lane-with-highest-priority.md).

Default budgets are separate for detail/main and coarse/minimap, with elastic borrowing only when the other lane has no current demand.

### Active-detail uses persistent liveness, then lowest importance

Pure insertion-order LRU is exactly wrong here: focal-point chunks fetch first (smallest priority number), so they're the *oldest* in cache, so they'd evict first under pressure — producing a center-outward eviction wave (visible in the chunkGrid debug overlay as green→red ripples).

Instead, active-detail evicts in this order (each key is a tiebreaker for the prior):

1. **`wanted` false before true** — chunks outside the persistent workspace wanted set go first. This is an explicit liveness bit, not an inference from whether an incremental publication happened to touch the request.
2. **`priority` descending** — among equally-live entries, the highest priority *number* (= farthest from focal, lowest importance) goes first.
3. **`lastSeenTick` ascending**, then **`insertedAt` ascending** — recency and insertion order are deterministic tiebreakers only.

Full publications refresh priority/touch metadata. Delta publications leave stable entries explicitly `wanted`, so an unchanged request is neither made undeliverable nor penalized for avoiding O(N) restamping.

## Interactions

- **Upstream**: [Planning Domain](planning-domain.md) produces the `RequestPlan` consumed by `submit`. The tick coordinator owns the call site (`pipeline/tickCoordinator.ts`).
- **Sideways**: `contentSource.ts` (binary fetch via [bridge.ts](../crates/lucida-web.md)) and `decodePool.ts` (a hardware-sized pool of web workers running `decode.worker.ts`).
- **Downstream**: the [Uploader](upload-pipeline.md) walks `getDeliverable()` and posts tier-labeled chunks to the GPU worker. Feedback returns through `markChunkEvicted` and `markChunkMissing`.

## Invariants

- **Demotion preserves bytes.** When an entity leaves the active set, its chunks don't drop — they move tier. They evict only under memory pressure, after the cheaper tiers are exhausted.
- **In-flight dedup is owner-addressed.** Dataset, entity, residency tier, and chunk coordinate form the key; one owner cannot cancel or replace another owner's work.
- **Recently-failed requests are skipped on next submit.** A failed fetch doesn't immediately retry. The wanted set carries the request forward; eventually the failure window expires.
- **Delivery is byte-bounded, not count-bounded.** Bigger chunks consume budget faster. The uploader receives `MAIN_VIEW_UPLOAD_BUDGET_BYTES` (8 MB on main view, 2 MB on minimap) per tick and uses a one-item soft cap.
- **Generated pending is not a failure.** A generated coarse request can return `pending`; the cache clears in-flight state and re-requests on a later submit instead of adding it to the recently-failed or rejected maps.

## Gotchas

- **Failure tracking is a window, not a permanent fail-list.** If a request fails repeatedly because the server can't serve it (e.g. a missing chunk), the cache will keep retrying with a backoff. There's no per-request retry budget.
- **Cache budgets are per-lane buckets, with limited elasticity.** Detail and coarse do not evict each other while both have demand. Borrowing only happens when one lane has no requested work.
- **Delivery is fair before it is globally greedy.** Each dataset's ready heap obeys planner priority; the workspace queue round-robins owners so a wide dataset cannot monopolize every frame.
- **In-flight fetches are not automatically current.** A chunk requested by an older camera/LOD plan may finish after a rebuild; it stays cached but is deliverable only if a newer submit refreshed that in-flight key. This prevents stale low-LOD arrivals from uploading into a zoomed-in cold state.
- **Worker skipped feedback is image-keyed, rejection is entity-keyed.** `markChunkEvicted` resolves `(imageId, c, chunkKey)` back through the cache entry before marking rejections, so collection tiles whose `entityId` differs from `imageId` do not repeatedly resend rejected chunks.
- **`submit` is called before upload in the same tick** — the planner refreshes wanted-generation on cached entries before `deliverToWorker` asks for deliverables. If you reorder these in `tickCoordinator.ts`, expect a one-frame upload latency or stale deliverability.
